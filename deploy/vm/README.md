# lolly.ing on one VM

lolly.ing runs on the existing UpCloud VM under openSUSE Leap 16.0. Caddy terminates
TLS. The lolly-work server serves the native web shell, control plane and live co-editing
gateway; the Chromium render worker runs alongside it. Neon Postgres holds workspace
records and permission-checked blobs. The current deployment uses a paid Neon plan.

The shell is a signed, qualified build mounted at `/app/shell/current`; it is no longer
proxied from lolly.tools. lolly.tools still hosts the public shell and the OSS CA, Penpot,
MCP and image-fetch API routes that lolly.ing proxies. These remain separate from the
private workspace catalog.

```
browser -> https://lolly.ing -> Caddy (:443)
   /api/(ca|penpot|mcp), /api/fetch-image -> https://lolly.tools (Cookie removed)
   /live/*                            -> optional live-relay service
   control plane, /ws/collab/*         -> server:8787
   native app, fonts, models, sw.js    -> server:8787 -> /app/shell/current
server:8787 -> Neon Postgres + private workspace pack
server:8787 -> render-worker:8791 (shared render-worker secret)
www.lolly.ing -> 308 https://lolly.ing{uri}
```

The base Caddyfile is generated by `node scripts/build-caddyfile.ts` from the same router
scan as the Vercel route table. Native serving uses `--serve-shell`; route-table tests cover
both modes. The deployed live-relay Compose/Caddy overlay is a separate release: preserve
and qualify it before another push, since replacing Caddy with an older generated file
would remove `/live/*`. Do not use the base push as a relay deployment recipe.

The canonical development checkout is `~/Build/lolly-work`. Backend feature worktrees
belong under its `.worktrees/`; frontend worktrees belong under `~/Build/lolly/.worktrees/`.
Use `git worktree move` and repair untracked dependency/pack links when relocating one.
Merge the latest backend main before exporting a release. Both `push.sh` and the
container build run `scripts/check-release-capabilities.ts`: an isolated memory-store
check of the owner/admin Agents API and desktop/mobile navigation. It also verifies
that ordinary members and signed-out callers cannot read the dashboard. The public
smoke check expects 401 from the agent activity route; a missing route is a failure.
Do not copy private workspace configuration into tracked files. When a backend worktree
needs its paired frontend, set `LOLLY_OSS_DIR` explicitly rather than relying on a sibling
checkout path. `push.sh` uses `LOLLY_DIR` for the source-pack checkout, so set that too
when running from a feature worktree. This keeps finished feature checkouts out of the
top-level Build directory.

For new servers, [UpCloud](../upcloud/README.md) and [Evroc](../evroc/README.md)

## Why the server starts as Debian

UpCloud has no openSUSE (or NixOS) template, and its storage import takes raw images only
(`.raw`, `.img`, `.iso`, optionally gz or xz), while openSUSE ships the Leap 16.0
Minimal-VM Cloud image as qcow2 only. So the server is deployed from UpCloud's Debian 12
template with a small system disk and a second, empty 50 GB disk; `bootstrap-opensuse.sh`
converts the image onto the empty disk; the Debian disk is then detached, and the server
boots Leap from the other. Leap's cloud-init (25.1) reads UpCloud's metadata service and
puts the ssh key on the user `sles`. Root cannot log in, so every script works as `sles`
and uses `sudo`.

Three things about the Leap image shape the kit:

- **SELinux is enforcing,** and openSUSE's Docker runs with `selinux-enabled`. A bind mount
  without a label is unreadable inside the container. `docker-compose.yml` gives the server's
  mounts a private label (`:Z`) and Caddy's a shared one (`:z`): `push.sh` validates the
  Caddyfile in a second Caddy container while the first runs. Named volumes need no label.
- **firewalld, and Docker bypasses it.** Ports Docker publishes are reachable whatever the
  firewalld zones say. Caddy's 80 and 443 are published on purpose; the server's 8787 only on
  `127.0.0.1`. Never publish another port without `127.0.0.1:`.
- **Root is locked.** `/opt/lolly-ing` belongs to `sles` (0700): `push.sh` copies files as
  `sles`, `secrets.sh` writes `.env` (0600) as `sles`, and `docker compose` runs through
  `sudo` (or as `sles`, who is in the `docker` group from the next login on).

## Keeping database usage bounded

The current paid plan removes the Free-plan quota that interrupted testing. Preserve the
existing account, autosuspend settings and usage alerts; an alert is not a hard spending
cap. Current plan terms and limits belong in the Neon account, rather than this runbook.
The server should still avoid queries on a clock:

- `LW_BACKGROUND_POLL_MS=0` (the compose default): the render and automation runners look for
  queued work at boot, on submission and after each finished item, never on a timer. A value
  shorter than Neon's 5-minute suspend delay, such as 300000, would keep the compute awake.
- The server's container health check is a TCP connect. The image's own check fetches
  `/healthz`, and every request to the server reads the design-system state from the database.
- `audit.headLog.intervalMinutes` is `0` in `instance.json`: the audit head is logged at boot
  only, not hourly.
- Pools close a connection after 30 s idle and give up connecting after 15 s
  (`server/src/store/pg-options.ts`).

What still wakes the database: people using lolly.ing (including a browser tab left open that
polls), a daily provider-credential check, and requests to the server. Native shell requests
also pass through the design-system state loader. Use a TCP/TLS check for frequent uptime
monitoring; schedule HTTP readiness probes sparingly so they do not prevent autosuspend.

Project-file and blob budgets remain enforced by `policy.projectFiles`. Provider metadata is
cached to reduce repeated database reads and egress. Check the account before changing limits.

## Custom instance domains

The kit also derives its HTTPS hostname from the private `instance.baseUrl`,
for example `https://workspace.example.com`. Use a canonical bare origin on port
443, without credentials, a path, query or fragment. `push.sh` validates this
before any remote copy, generates the matching Caddy configuration and probes
that hostname by IP after restart. The checked-in Caddyfile keeps the lolly.ing
defaults; a custom file is generated privately for the deploy.

Custom domains have no implicit redirect aliases. Add only hostnames you own and
intend to serve, using `--redirect` on push and smoke. Register the new
`https://workspace.example.com/api/auth/callback` with the configured identity
provider, and replace the example client IDs, owners, admission rules and group
mappings with this instance's values. Keep the current private secrets and
provider settings unless performing an explicit new-instance setup.

```sh
deploy/vm/push.sh sles@<ip> --internal-tls --redirect design.example.com
deploy/vm/smoke.sh <ip> --insecure --domain workspace.example.com \
  --redirect design.example.com --idp github --authorize-origin https://github.com
```

The smoke command checks unauthenticated health/readiness, sign-in HTML or an
HTTPS provider redirect, private catalog/agent/room refusal and shell serving.
On custom domains it checks an external provider only when both `--idp` and
`--authorize-origin` are supplied; otherwise it prints that check as skipped.
Choose the ID of a configured external provider and its actual authorization
origin. This supports password-only and non-Google instances without probing an
unconfigured Google provider. The lolly.ing defaults still check primary Google
and the www redirect. Complete a real owner sign-in and shared session/export
check as deployment acceptance; smoke does not exercise passkey enrollment.

For the managed render worker, set `LOLLY_WEB_BASE` in the VM's private `.env` to
this same bare HTTPS origin. Compose retains `https://lolly.ing` when it is unset.
Before starting the worker or restarting Work, push parses Compose's resolved
configuration with the host's Python 3 and refuses a mismatched worker origin.
It never sources or prints the private environment file. Preserve all other keys.

This is still the openSUSE host kit on either qualified provider. Its compatible
storage paths remain `/opt/lolly-ing` and `packs/lolly-ing`, and the automatic
pack builder still selects the SUSE profile. Prepare and qualify the intended
pack at that path for another brand, or use the generic Compose/Helm shape and
its own configuration. Public APIs still use the reviewed shell origin until
standalone parity is accepted. The base-only push does not manage extra relay or
database overlays; preserve their complete file list in an operator-managed
release, as described below. None of these options changes DNS automatically.

## Runbook

These steps describe provisioning a new VM and the original DNS transition. The existing
lolly.ing VM already serves the native shell. For an update, use the qualified artifact
with `LOLLY_SHELL_DIST`, explicit `LOLLY_DIR` and the intended `LOLLY_REV`, preserve private
config/secrets and the live-relay overlay, and follow the Native web shell section below.
Rehearse a rollback to a retained native release before retiring an earlier one.

The optional Chromium worker uses the `render` Compose profile. Set
`render.worker.url` to `http://render-worker:8791` and a suitable timeout (60000 ms)
in the private `instance.json`, and add `LW_RENDER_WORKER_SECRET` to the VM's
private `.env`. `push.sh` then builds and starts the worker before restarting
the server. Both services use that same key. Preserve every other secret when
editing `.env`; the worker receives only its render key, with no database or
sign-in credentials. It drives the signed shell at `LOLLY_WEB_BASE` (default
`https://lolly.ing`, or the configured custom instance origin) using a
five-minute read-only catalog ticket scoped to the caller's groups and current
brand revision. This ticket cannot sign in, read projects or call write routes. The worker runs
with a read-only filesystem and temporary browser storage, and accepts at most
two simultaneous jobs. Its port stays inside the Compose network. Test an
authenticated tool export and PNG/PDF rendering after deployment; health alone
does not prove Chromium can start.

Run everything from the root of this repository on your own machine. `<ip>` is the server's
public IPv4 address. Your ssh key is `~/.ssh/id_ed25519.pub`.

1. **Create the server.** In the UpCloud hub, **Deploy server**:
   - Location: **Frankfurt** (de-fra1).
   - Plan: **Cloud Native**, 2 CPU, 4 GB (`CLOUDNATIVE-2xCPU-4GB`).
   - Storage: the template disk at **10 GB**, then **Add new device**: **50 GB, MaxIOPS**,
     empty. openSUSE goes on this one.
   - Operating system: **Debian 12** (Bookworm).
   - Login: **SSH key**, paste `~/.ssh/id_ed25519.pub` (UpCloud puts it on `root` for Debian).
   - Optionals: **Metadata service on**. Leap's cloud-init reads the key and the host name from
     it; without it nobody can log in to Leap.
   - Hostname `lolly-ing`, then **Deploy**.

   If UpCloud's firewall is enabled for the server, allow 22, 80 and 443 (TCP) and 443 (UDP).
2. **Put openSUSE on the 50 GB disk.** On the Debian server, first the plan, which writes
   nothing:
   ```bash
   ssh root@<ip> 'bash -s' < deploy/vm/bootstrap-opensuse.sh
   ```
   It refuses unless exactly one disk besides Debian's exists and that disk is empty (at least
   20 GiB, no partitions, no signature, not mounted, not swap, not held by LVM or RAID), and
   names it, usually `/dev/vdb`. Check the size, then run it again with that device:
   ```bash
   ssh root@<ip> 'bash -s -- /dev/vdb' < deploy/vm/bootstrap-opensuse.sh
   ```
   It installs `qemu-utils`, downloads `Leap-16.0-Minimal-VM.x86_64-Cloud.qcow2` (about
   320 MB) from download.opensuse.org, checks its SHA-256 and that it fits, writes it to the
   disk as raw (1.4 GiB) and powers the server off (ssh then reports the connection closed).
   It takes a minute or two: keep the connection up (and your machine awake) until it prints
   `Done`. If the connection drops before that, run the plan again; if it now refuses because
   the disk carries a signature, the write had started: see
   [If Leap does not come up](#if-leap-does-not-come-up). With `--tumbleweed` it writes
   openSUSE Tumbleweed instead, whose user is `opensuse` where this runbook says `sles`; use
   it only if Leap will not come up, through that section.

   Then, in the hub, open the server's **Storage** tab, **detach** the 10 GB Debian disk
   (keep it until step 14: it is the way back), and **start** the server. It boots Leap from
   the 50 GB disk. The host key changed, so forget the old one, then log in as `sles`:
   ```bash
   ssh-keygen -R <ip>
   ssh sles@<ip> 'grep PRETTY_NAME /etc/os-release; sudo -n true && echo "sudo: ok"; getenforce; df -h /'
   ```
   It answers openSUSE Leap 16.0, `sudo: ok`, `Enforcing` and a `/` of about 50G. Without
   `sudo: ok`, `sles` has no passwordless sudo and the scripts below cannot work. The image
   is 1.4 GiB and grows its root partition and XFS filesystem to the whole disk at first boot;
   a `/` of about 1.4G means that did not happen. Grow it by hand
   (`sudo growpart /dev/vda <partition>` with the partition `lsblk` shows for `/`, then
   `sudo xfs_growfs /`); provision.sh refuses a `/` under 15 GiB and prints that command.
   If ssh fails, see [If Leap does not come up](#if-leap-does-not-come-up).
3. **Provision.**
   ```bash
   ssh sles@<ip> 'sudo bash -s' < deploy/vm/provision.sh
   ```
   Updates; Docker with the compose and buildx plugins; rsync and openssl; firewalld letting
   ssh, http, https and HTTP/3 through, then Docker (after firewalld, so it adds its own zone);
   a 2 GB swap file labelled `swapfile_t`; os-update's daily security updates, which reboot
   when needed; the host name; ssh with keys only and no root login (checked with `sshd -t`
   before sshd reloads, after confirming `sles` keeps its key); `/opt/lolly-ing` (0700, owned
   by `sles`); `sles` in the `docker` group. It refuses anything but openSUSE Leap 16 or
   Tumbleweed, and a `/` that did not grow, and is safe to run again. If it says so, reboot:
   `ssh sles@<ip> sudo reboot`.

   Then give `sles` a password, for the hub's console: once the Debian disk is gone it is the
   only way in if ssh ever fails (ssh keeps refusing passwords). Keep it in your password
   manager:
   ```bash
   ssh -t sles@<ip> sudo passwd sles
   ```
4. **Configure.** `cp deploy/vm/instance.json.example deploy/vm/instance.json`. Put the GitHub
   OAuth App's client id in the `github` entry, or delete that entry until there is one (an
   entry without its secret still shows on the sign-in page, and the setup checks warn about
   it). Its callback URL is the same as Google's: `https://lolly.ing/api/auth/callback`.
5. **Secrets.**
   ```bash
   deploy/vm/secrets.sh sles@<ip> <path to catalog-signing.key.pem>
   ```
   It asks, without echo, for `LW_SESSION_SECRET` and `LW_LINK_SECRET` (paste the values the
   Vercel project uses; see below), the Google client secret, the Neon **direct** connection
   string (Neon console, Connect, with connection pooling off: the host has no `-pooler`; the
   Vercel project has it as `DATABASE_URL_UNPOOLED`) and, optionally, the GitHub client secret.
   Enter keeps what the VM already has. The signing key PEM is checked against
   `lolly/keys/catalog-signing.pub.jwk.json` and stored as a one-line JWK. The file is
   `/opt/lolly-ing/.env`, mode 0600, owned by `sles`.
6. **Deploy with Caddy's own certificates.**
   ```bash
   deploy/vm/push.sh sles@<ip> --internal-tls
   ```
   It builds `packs/lolly-ing` if it is missing (Lolly `ae49bf82f`, profile `suse`, `og`
   excluded), checks that `Caddyfile` is current and that `instance.json` with the pack passes
   the production setup checks, copies the source (tracked and new files, without plans,
   build output, dependencies and data packs), the pack and the configuration to
   `/opt/lolly-ing` as `sles`, then, with `sudo docker compose`, validates the Caddyfile
   (`caddy validate`), builds the image, restarts the server (migrations run at boot),
   reloads Caddy and waits for `/healthz`. The user defaults to `sles` (`LOLLY_VM_USER`), so
   `push.sh <ip>` is the same.
7. **Check the VM before DNS points at it.**
   ```bash
   deploy/vm/smoke.sh <ip> --insecure
   ```
   Every check must pass: `/healthz` and `/readyz` 200, the sign-in page, the redirect to Google
   with the lolly.ing callback, `/catalog/tools/index.json` 401 signed out, `/sw.js` and `/`
   from lolly.tools with HSTS, `/ws/collab/<id>` 401 from the gateway without a session, and
   `www` 308. A browser cannot be used yet: lolly.ing sends HSTS, so browsers refuse Caddy's
   own certificate.
8. **Bring the Vercel rollback up to this code.** Before DNS leaves Vercel, its production
   deployment must be built from this checkout or later. The build live on 2026-10-03 is
   older: it takes its migration lock over the pooled `DATABASE_URL`, where the pooler keeps
   it, so cold starts hang until the 300 s function timeout; it has no boot deadline; and it
   tells the Lolly app to open live rooms that Vercel cannot serve. From the checkout
   linked to `lolly-ing` (`deploy/vercel/README.md`, section 6; step 6 built `packs/lolly-ing`):
   ```bash
   vercel env ls production                         # DATABASE_URL_UNPOOLED is listed
   vercel env add LW_BACKGROUND_POLL_MS production  # enter 0
   vercel deploy --prod --archive=tgz
   curl -s https://lolly.ing/api/v1/instance        # "engineVersion" is a version, not null
   deploy/vm/smoke.sh 76.76.21.21
   ```
   `DATABASE_URL_UNPOOLED` comes with the Neon integration; migrations run over it. Against
   Vercel, `smoke.sh` passes every check but `/ws/collab/<id>` and `www`, which only the VM
   answers. DNS still points at Vercel, so this build serves lolly.ing until step 10.
9. **Lower the DNS TTL.** At Namecheap, set the TTL of the `A @` and `A www` records (today
   76.76.21.21, Vercel) to 5 minutes, then wait for the old TTL to pass before step 10. Doing
   this at the start of the runbook saves the wait.
10. **Cut DNS.** At Namecheap, point `A @` and `A www` at `<ip>` (replace 76.76.21.21; a `www`
    CNAME to Vercel becomes an `A` record). Wait until `dig +short lolly.ing @1.1.1.1` and
    `dig +short www.lolly.ing @8.8.8.8` both answer `<ip>`.
11. **Switch to Let's Encrypt.**
    ```bash
    deploy/vm/push.sh sles@<ip>
    ```
    Caddy obtains certificates for both names over ports 80 and 443 within a minute;
    `push.sh` waits for `https://lolly.ing/healthz` through Caddy. Until then visitors whose
    resolver already has the new address see a certificate error, so do steps 10 and 11 together.
12. **Check again,** without `--insecure`: `deploy/vm/smoke.sh <ip>`.
13. **Acceptance.** The table in plans/74 "Acceptance", plus live co-editing: open the same
    team session in two browser profiles and edit in one; the other follows live, and a
    redeploy (`push.sh` again) reconnects both without losing an edit.
14. **Delete the Debian disk.** In the hub, **Storage**, delete the detached 10 GB Debian disk:
    UpCloud bills it for as long as it exists, and nothing needs it once Leap runs.

Nothing changes at Google: the redirect URI stays `https://lolly.ing/api/auth/callback`.

### If Leap does not come up

Until step 3 gives `sles` a password, nobody can log in at the hub's console: root is
locked on Leap, `sles` has no password, and ssh takes keys only. The Debian disk, kept
until step 14, is the way back.

- **ssh waits or is refused, and the hub's console shows a first-boot wizard
  (jeos-firstboot):** cloud-init found no metadata, so no key reached `sles`. The image skips
  the wizard only when cloud-init found a datasource, and logins wait for the wizard. If the
  metadata service was off, stop the server, turn it on in the server's settings and start
  the server again. Otherwise finish the wizard (it sets a root password), log in at the
  console as root and see why: `cloud-init status --long`.
- **Anything else** (it does not boot, ssh refuses your key, the write in step 2 was cut
  short, or you want Tumbleweed instead): write the 50 GB disk again from Debian.
  1. If the server still runs Debian (the write was cut short before you detached
     anything), go to 3. Otherwise stop the server. In **Storage**, attach the Debian disk
     again as the boot disk, beside the 50 GB one (if the hub offers no boot-disk choice,
     detach the 50 GB disk, attach the Debian disk, then attach the 50 GB disk again).
     Start the server.
  2. Its host key is Debian's again: `ssh-keygen -R <ip>`.
  3. The plan, which lists what the 50 GB disk holds and erases nothing (and refuses
     anywhere but Debian):
     ```bash
     ssh root@<ip> 'bash -s -- --overwrite' < deploy/vm/bootstrap-opensuse.sh
     ```
  4. If it names the 50 GB disk, write it again (add `--tumbleweed` before the device for
     Tumbleweed). `--overwrite` needs the disk named and keeps every other check: nothing on
     the disk mounted, swap or held, and exactly one disk besides Debian's:
     ```bash
     ssh root@<ip> 'bash -s -- --overwrite /dev/vdb' < deploy/vm/bootstrap-opensuse.sh
     ```
  5. Detach the Debian disk and start the server, as in runbook step 2.

### Session and link secrets

Use the same `LW_SESSION_SECRET` and `LW_LINK_SECRET` as the Vercel project. The session
secret also derives the key of the audit log's MACs: rows written with one key fail
verification under another, so the console and `/api/v1/audit/head` would report the chain
broken at the first row the other host wrote. The two secrets also sign sign-in sessions and
share links. If the Vercel values are lost, `secrets.sh` generates new ones on the VM and says
so; set the same new values on Vercel before any rollback.

To replace both on both hosts at once (Vercel keeps them write-only, so the old values cannot
be read back), run `deploy/vm/rotate-secrets.sh sles@<ip>` from this checkout, after `push.sh`
has put this code on the VM. It first records the audit log's head inside the running server
(`scripts/audit-head.ts`), then generates the values, writes them into `/opt/lolly-ing/.env`
and onto the Vercel project `lolly-ing` (production) without printing them, recreates the
server, and prints the steps left: redeploy the Vercel project, sign in once, then record the
audit log's retired-key boundary once on the VM with that head (`scripts/audit-retire-key.ts`,
see [docs/audit.md](../../docs/audit.md#rotating-the-session-secret)). If it stops part way it
reports the state of the VM and of each Vercel variable; running it again starts over. Everyone signs
in again and issued share links stop verifying.

## Rollback

For a shell-only rollback, first verify the retained release and its signed catalog. Switch
`/opt/lolly-ing/shell/current` to that immutable release with a temporary symlink and atomic
rename, then check liveness, sign-in, private-catalog access and a fresh collaboration room.
Preserve old hashed chunks for tabs that are already open. The release identity hashes every
file name and byte, so static-only changes receive a separate directory even when index.html
is unchanged.

For a backend rollback, qualify the previous image against the current migrations before
restarting the server. Do not restore an old database over active collaboration as a rollback
experiment. Keep an isolated, verified database restore available for disaster recovery.

A DNS rollback to Vercel needs its own rehearsal: its private workspace deployment must
contain the same routes, configuration, engine pin, secrets and compatible migrations.
Vercel functions cannot supply the VM's WebSocket gateway, worker or live relay. The public
lolly.tools deployment is not a replacement for the private workspace deployment. Do not
change workspace DNS until these differences are understood and the target is verified.
Probe the prepared Vercel target directly before changing DNS:

```bash
curl -s --resolve lolly.ing:443:76.76.21.21 https://lolly.ing/api/v1/instance
```

Its `engineVersion` must match the intended engine pin; also check readiness, sign-in and
private-catalog denial without a session. A successful instance probe alone does not qualify
live collaboration or the worker on that target.

## Operating

On the VM (`ssh sles@<ip>`), in `/opt/lolly-ing`. `sles` is in the `docker` group, so
`docker` works without `sudo` from the second login on:

- `docker compose ps`, `docker compose logs -f server`, `docker compose logs -f caddy`.
- A new deploy is `push.sh` again. The server gets `SIGTERM` and up to 60 s
  (`stop_grace_period`) to save every live co-editing room as a session revision.
- A secret change is `secrets.sh` again, then `docker compose up -d --force-recreate server`.
- Logs rotate at 10 MB, five files per service. Certificates live in the `caddy_data` volume;
  keep it, Let's Encrypt limits how often the same names are issued.
- Updates: `os-update.timer` installs security updates daily and reboots when one needs it;
  Docker starts at boot and brings both containers back (`restart: unless-stopped`).
  `systemctl list-timers os-update.timer` shows the next run, `journalctl -u os-update` the
  last ones.
- SELinux: a container that cannot read a mounted file usually means a bind mount without
  `:z` or `:Z`. Denials are in `sudo journalctl -k | grep avc` (or `sudo ausearch -m avc` where auditd
  runs). Keep SELinux enforcing.
- Firewall: `sudo firewall-cmd --list-all`. Remember it does not cover ports Docker publishes.
- Recovery: ssh takes keys only, and the hub's console needs a password. Root has none;
  `sles` has the one runbook step 3 gave it (`sudo passwd sles` sets another). ssh still
  refuses it.

A WebSocket cannot go through Vercel's rewrite to another origin (rewrites carry plain HTTP
requests with a 120 s cap), so live co-editing needs this host or a gateway of its own; the
Vercel project keeps it off.

### Native web shell

Set `instance.shellDir` to `/app/shell/current` in the private instance config and pass `LOLLY_SHELL_DIST=/absolute/path/to/qualified/dist` to `push.sh`. Build and verify the signed release before deployment. The setup check uses this local path while the deployed configuration keeps the container path. Each release receives an immutable directory identified by all of its file names and bytes, including static assets, and an atomic `current` pointer. Older hashed app chunks stay available to open tabs; unchanged release files use hard links. Secrets and other configuration fields are preserved.

For the native Work release, keep the plugin review recording at `shells/web/public/review/agent-collaboration-review.mp4` before building. The public plugin continues to use its canonical `lolly.tools` recording URL. Work redirects the previous `/info/media/agent-collaboration-review.mp4` path to `/review/agent-collaboration-review.mp4`, preserving native links while leaving the recording outside the offline documentation bundle.
