# Lolly Work for Dokploy

The `lolly-work/` directory is the upstream-owned submission package for
`Dokploy/templates/blueprints/lolly-work/`. It is generated by
`node scripts/marketplace-packages.ts`, shares the VM runtime configuration and
pins the same public server image and neutral shell. There is no Caddy container
or published application/database port: Dokploy owns HTTPS and proxy routing.

Before deployment, edit the imported environment and domain to set
`LOLLY_DOMAIN` and `LOLLY_OWNER_EMAIL`. Built-in email/password sign-in is the
default; it requires no external identity account or mail service. The
template generates database/session/link/credential secrets. Keep those values
on updates. After boot, use the server terminal to run
`node scripts/password-link.ts --email OWNER_EMAIL`. Give the resulting single-use,
seven-day setup link privately to the owner. It authorizes the account without
proving mailbox ownership. Other members need invitations and password links
from **People**, or an operator-reviewed admission policy.

For SSO instead, set `LOLLY_AUTH_MODE=oidc`, `LOLLY_OIDC_ISSUER` and
`LOLLY_OIDC_CLIENT_ID`; add `LW_IDP_CLIENT_SECRET` if required. The callback is
`https://YOUR_DOMAIN/api/auth/callback`; the owner email must be verified by that
provider.

Import the Compose file and `template.toml` through Dokploy's template import
flow. Confirm the generated domain uses HTTPS and WebSockets. First deployment
downloads the checksum-pinned neutral archive before Work starts; allow its disk
and network requirements in the shared distribution README. The optional render
worker is not installed.

## Submission and subsequent updates

1. Complete install, actual owner/member sign-in, private-access denial, output,
   restart, installed-instance upgrade and independent restore on an isolated
   Dokploy target. Capture exact source, blueprint and image identities.
2. Fork [Dokploy/templates](https://github.com/Dokploy/templates), copy the four
   blueprint files into `blueprints/lolly-work/`, run their metadata checks and
   test the generated import on Dokploy. Submit the reviewed PR with evidence.
   Submission has not occurred merely because these files exist upstream.
3. Keep the project source/docs links, name and icon in the listing. Request
   upstream attribution; Dokploy controls its catalogue review and merge.
4. For a new matched release, update the common release record, regenerate, test
   an installed-instance upgrade and submit the resulting blueprint/version PR.
   Changing a public template does not update existing installations.

For customer upgrades, preserve the deployment's project/volume identity,
environment, stored configuration, keys, database and old content. Back up and independently restore
before replacing the server. Compare generated changes to the existing deployment
and retain operator settings. Do not reimport generated secrets over a live
installation or remove its volumes. New PostgreSQL major versions need their own
database migration plan. A server-image downgrade cannot undo SQL migrations.

The blueprint is a preparation candidate until the target evidence and catalogue
review pass. [Dokploy's contribution and update requirements](https://github.com/Dokploy/templates/blob/canary/CONTRIBUTING.md).
