# Lolly Work for Coolify

The `lolly-work/docker-compose.yml` file is a project-owned Compose recipe for
[Coolify](https://coolify.io). It is generated by
`node scripts/marketplace-packages.ts`, shares the VM runtime configuration and
pins the same public server image and neutral shell. There is no Caddy container
and no published application or database port: Coolify's proxy owns HTTPS and
routing, and WebSocket upgrades pass through it.

It is a recipe to import, not a Coolify catalogue entry. Coolify's built-in
one-click catalogue has a popularity requirement this project does not meet, so
catalogue admission is not pursued yet. The file carries Coolify's header
comments (`# documentation`, `# slogan`, `# tags`, `# port`) so it can be offered
later without changes, but it has no `# logo` because that path resolves only inside
Coolify's own repository.

**Status: not qualified on a live Coolify.** The file is checked in CI-free local
tests for structure only (magic variable names, no `build:`, no host ports). It has
not been imported into a running Coolify. Run the owner, member, privacy, restart,
upgrade and restore checks from the
[ready-made package guide](../../docs/ready-made-package.md) on an isolated Coolify
before you rely on it.

## Install

1. In Coolify, open a project and choose **Add Resource**, then **Docker Compose
   Empty**. Paste `lolly-work/docker-compose.yml` and save.
2. Under the `server` component, set **Domains** to the public HTTPS address, for
   example `https://work.example.com`. Point that DNS name at the Coolify server
   first. Coolify routes the domain to the server's internal port 8787. The domain
   must be a plain DNS name served over HTTPS: Lolly refuses an address with a port
   or path.
3. In **Environment Variables**, set `LOLLY_OWNER_EMAIL`. Coolify blocks the
   deployment until it has a value. `LOLLY_DOMAIN` needs no entry: the recipe
   takes it from the domain in step 2 through `SERVICE_FQDN_SERVER`.
4. Deploy. The first deployment downloads the checksum-pinned neutral archive
   before Work starts; allow its disk and network requirements in the shared
   distribution README. The optional render worker is not installed.

## Generated secrets

Coolify generates each of these once and keeps them across deployments:

| Variable the server reads | Coolify generator | Value |
|---|---|---|
| `POSTGRES_PASSWORD` and the password in `DATABASE_URL` | `SERVICE_PASSWORD_64_POSTGRES` | 64 letters and digits, URL-safe |
| `LW_SESSION_SECRET` | `SERVICE_PASSWORD_64_SESSION` | 64 letters and digits |
| `LW_LINK_SECRET` | `SERVICE_PASSWORD_64_LINK` | 64 letters and digits |
| `LW_CREDENTIAL_SECRET` | `SERVICE_PASSWORD_64_CREDENTIAL` | 64 letters and digits |

The server needs at least 32 characters for each of the three application secrets.
Do not edit or delete these values on a live installation.

## Owner sign-in

Built-in email and password sign-in is the default; it needs no external identity
account or mail service. After boot, open the `server` component's terminal and run
`node scripts/password-link.ts --email OWNER_EMAIL`. Give the resulting single-use,
seven-day setup link privately to the owner. It authorizes the account without
proving mailbox ownership. Other members need invitations and password links from
**People**, or an operator-reviewed admission policy.

For SSO instead, set `LOLLY_AUTH_MODE=oidc`, `LOLLY_OIDC_ISSUER` and
`LOLLY_OIDC_CLIENT_ID`; add `LW_IDP_CLIENT_SECRET` if the provider needs one. The
callback is `https://YOUR_DOMAIN/api/auth/callback`; the owner email must be
verified by that provider.

## Updates and restore

Coolify copies a pasted or one-click Compose file when you create the service.
Later changes to this repository do not merge into it. To update:

1. Take a backup and pass an independent restore first (see the
   [ready-made package guide](../../docs/ready-made-package.md#back-up-restore-and-update)).
   Back up the `pgdata`, `state` and `keys` volumes; Coolify prefixes their names
   with the resource ID.
2. Compare the new `lolly-work/docker-compose.yml` with the service's **Source
   Compose**. Copy only the changed image pins, shell URL and checksum, catalogue
   generation and key, and any new script text. Keep the service, its volumes, its
   generated secrets and your environment values. Never create a new service to
   update an old one, because a new service generates new secrets.
3. Save and redeploy.

New PostgreSQL major versions need their own database migration plan. A server-image
downgrade cannot undo SQL migrations.

## Qualify before relying on it

Confirm on an isolated target: the generated domain reaches HTTPS with WebSockets,
`LOLLY_DOMAIN` equals the host name without a scheme, the one-time `content`
component finishes (it is marked `exclude_from_hc`), volumes persist across a
redeploy, and generated secrets stay unchanged after saving the environment.
